# Engine choice and benchmark

**TL;DR** — The app uses **Stockfish 19 lite NNUE, single-threaded WebAssembly (1.8 MB)** in a pool of
Web Workers, at **depth 14 with MultiPV 1 + `searchmoves`** for each candidate move, after a cheap
depth-10 triage pass. On opening positions it classifies mistakes as well as the 99 MB full build and as
well as native Stockfish, needs no install, and runs on any static host.

| Option | Download | Install | Verdict |
| --- | --- | --- | --- |
| Native Stockfish (v2 app) | — | user installs Python + Stockfish | fastest per core, but needs a local server; adoption killer |
| SF19 full NNUE WASM | 99 MB | none | same accuracy as lite here, 1.7× slower, 6.6× slower to load → rejected |
| **SF19 lite NNUE WASM** | **1.8 MB** | none | **chosen** |
| Multi-threaded WASM | 1.6–94 MB | none | needs COOP/COEP headers (not available on GitHub Pages) → replaced by a pool of single-threaded engines |
| ASM.js build | 3 MB | none | much slower; not shipped |
| Lichess cloud eval | 0 | none | rarely contains the bad move itself; Lichess asks for light use → not used |

The rest of this page is the benchmark report produced by `scripts/bench/bench.mjs`.

# Engine benchmark: opening-mistake detection

Every number below was measured on this machine by bench.mjs. Aggregate data is in `docs/engine-benchmark/results.json`; per-run files are regenerated by the harness. Anything estimated rather than measured is labelled (derived).

## Recommendation

**Build: Stockfish 19 lite single-threaded WASM (1.8 MB) for every preset.** Use **MultiPV 1** plus a `go depth D searchmoves <move>` search for each candidate that is not the best move. Run a pool of hardwareConcurrency-1 engines.

| Preset | Build | Depth | MultiPV | ms/position median (p90), 1 engine | Severity agree [95% CI] | P / R loss>=5 | P / R loss>=10 | Loss MAE |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| fast | lite | 10 | 1 | 43 (72) | 88.0% [84.7, 90.7] | 92.4 / 92.4 | 91.2 / 90.4 | 1.98 |
| **balanced (default)** | lite | **14** | **1** | 353 (558) | 89.6% [86.4, 92.1] | 94.6 / 91.9 | 93.8 / 93.0 | 1.48 |
| deep | lite | 16 | 1 | 984 (1764) | 90.0% [86.9, 92.4] | 94.7 / 93.6 | 92.1 / 92.1 | 1.44 |

Why:

- **Depth 14 is the knee.** Loss error drops significantly up to d14, and nothing improves measurably after it:
  - d12 to d14 (MPV 1): MAE -0.35 win-% points, 95% CI [-0.56, -0.18]; severity McNemar p=0.06.
  - d14 to d16 (MPV 1): MAE -0.04 [-0.17, +0.09]; severity p=0.86.
  - d8 is clearly worse than d14: severity p=0.002, MAE +0.73.

  Every build and MultiPV setting lands at 89.6-90.4% severity agreement at d14.
- **The fast preset (d10) classifies about as well as d14 but ranks worse.** Class agreement is not significantly different (p=0.34). Its loss MAE is 0.50 points worse ([-0.71, -0.31]), so impact ranking (times played x loss) is noisier. Use it for a quick first pass or slow devices.
- **"Deep" buys nothing measurable against this reference.** It is 2.8x the balanced cost; offer it as an opt-in only. Lite d18 (MPV 3, run on the 4-engine pool) reached 90.7% at 3.3 s per position per engine, which is also not significantly better.
- **MultiPV 1 instead of 3.** This changed the first design draft, which used "MultiPV k (default 3)"; `docs/ARCHITECTURE.md` reflects the change.
  - Accuracy is the same: at d14, MPV 1 vs 3 gives McNemar p=0.86 and MAE change +0.05 [-0.10, +0.24]. MPV 3 vs 5 gives p=1.0.
  - MPV 1 is 1.7x faster on this set (d14 median 353 vs 600 ms; d12 125 vs 233 ms), even though it needs more searchmoves searches (3.47 vs 2.57 searches per position).
  - The real app usually has 1-2 candidate moves per position. (derived) From the measured per-search means at d14 (MPV 1 root search 156 ms, MPV 3 root search 531 ms, one searchmoves search 80-92 ms), a 1-candidate position costs 156-248 ms with MPV 1 vs 531-611 ms with MPV 3. That is 2.5-3.4x cheaper.
  - The refutation and the engine line come from the PVs anyway. Use MPV 3 only on demand, for example when a detail view or training needs "other good moves".
- **Reject the full 99 MB WASM build.**
  - Same class accuracy as lite: p=0.87 at d14, p=0.16 at d12.
  - 1.7x slower per position: d14 1026 vs 600 ms, d12 400 vs 233 ms. It runs at ~300 knps vs ~580-620 for lite.
  - 6.6x longer init (852 vs 130 ms median), before even counting the 99 MB download.
  - Higher loss MAE against the SF16 reference (+0.37, CI [+0.19, +0.55]).
- **The pool design works on this 4-vCPU box.** Lite d12 over all 150 positions with 1/2/3/4 engines took 37.1 / 18.6 / 13.0 / 9.6 s. That is a 1.99x / 2.86x / 3.86x speedup, and per-engine speed stayed flat (611 knps with 1 engine, 602 knps each with 4).
  - (derived) The balanced preset on 150 positions: 57.6 s of single-engine search time, so about 20 s with 3 engines on this machine.

## Setup

- **Machine:** KVM VM with 4 vCPUs ("Intel Xeon Processor @ 2.10GHz", 1 thread per core, AVX-512), 15 GB RAM, Node v22.22.0.
- **Builds:**
  - Native Stockfish 16 (/usr/games/stockfish, Debian 16-1build1). Its `compiler` command reports "64bit SSE2", a generic build without POPCNT/AVX2.
  - SF19 lite single (stockfish-19-lite-single, 1.8 MB).
  - SF19 full single (stockfish-19-single, 99 MB), both from npm stockfish@19.0.0.
  - All candidate runs use Threads 1 and Hash 16.
- **WASM in Node:** the stockfish.js glue refuses to export its factory inside a Node worker_thread (it assumes it is an Emscripten pthread there). So each WASM engine runs as its own Node process using the package's CLI mode (UCI over stdin/stdout). It is the same WASM on the same V8, and the engines run truly in parallel.
- **Test set** (testset.json, seed 20261008, chessops 0.15.1 replay of the lichess openings TSVs; all 3865 lines parsed; rebuilding from the seed gives identical output):
  - 150 distinct positions, 6-7 at each ply from 2 to 24; 73 with White to move, 77 with Black.
  - 450 (position, move) pairs:
    - 133 theory continuations;
    - 167 uniformly random legal moves (a second random move where no theory move exists);
    - 150 of the reference's 2nd/3rd-best moves (picked with a seed).
  - Reference severity mix: 278 ok, 58 inaccuracy, 33 mistake, 81 blunder.
  - Run order is shuffled.
- **Reference:**
  - SF16 at depth 22, MultiPV 3, Hash 64, Threads 1.
  - ucinewgame before every position, so results do not depend on order.
  - Each candidate not among the 3 PV moves gets `go depth 22 searchmoves <move>` from the same root.
  - Every line reached depth 22. Run as 4 parallel processes, 490 s in total (median 12.4 s per position under that load).
- **Method under test:** identical to the reference at depth D and MultiPV k.
  - One fresh engine process per configuration.
  - The hash is kept between positions (no ucinewgame).
  - Wall time per position covers the MultiPV search plus all searchmoves searches.
- **Metrics:**
  - winPct(cp) = 50+50*(2/(1+exp(-0.00368208*cp))-1); a mate counts as 100 or 0.
  - loss = max(0, winPct(MultiPV-1 score) - winPct(move)).
  - Severity: blunder>=15, mistake>=10, inaccuracy>=5.
  - 95% CIs are Wilson intervals. Paired tests use an exact McNemar test on per-pair class correctness, plus a position-clustered bootstrap (2000 resamples) for the MAE difference.

What these numbers say:

- **Errors are between neighbouring severity classes.** At lite d14 MPV 3, no reference "ok" move is called mistake or blunder, and no reference mistake or blunder is called "ok". The confusion matrix (reference rows ok/inacc/mistake/blunder, config columns in the same order): ok 267/11/0/0; inacc 10/40/8/0; mistake 0/9/17/7; blunder 0/0/0/81.
- **Best move:** exact agreement is 57-74%, because many opening moves are near-equal. But the configuration's best move is acceptable by the reference (loss < 5) in 98.5-100% of the cases the reference evaluated (130-148 of 150 positions per configuration).
- **Ceiling:** native SF16 at d18 agrees with SF16 d22 on only 92.2% of severity classes. So ~90% is close to the ceiling for this reference, and most of the remaining disagreement is the reference's own noise at class boundaries.
- **Hash state alone moves results by ~3 points.** Lite d12 MPV3 gave 85.8% as one engine and 88.9% on the 4-engine pool; the only difference is which positions shared a hash table (McNemar p=0.054). Treat differences of 3 points or less between single runs as noise.
- **Non-random subset** (theory and 2nd/3rd-best moves, 283 pairs; the harder, more realistic cases):
  - Severity agreement: 80.6% (native d8), 87-89% (lite d10-12), 91.5-92.9% (lite d14).
  - The subset has only 45 positives at loss>=5 and 14 at loss>=10, so its P/R values have intervals of +-10-25 points (full tables in results.json).

### Reproducibility

- Single-threaded searches are deterministic: repeats of lite d12 and native d12 gave identical nodes and evals on 150/150 positions.
- Run totals reproduced within 4% (38.0 vs 36.6 s; 31.8 vs 31.6 s).
- Individual positions vary +-15-20% (p10-p90 ratio between runs 0.82-1.20).

## Reproduce

```sh
npm --prefix scripts/bench install   # separate install: the stockfish npm package is ~160 MB
cd scripts/bench
node bench.mjs all            # runs every missing step; --force re-runs everything
node bench.mjs run --engine lite --depth 14 --multipv 1      # engines: native | lite | full
node bench.mjs parallel --engine lite --depth 12 --workers 1,2,3,4
node bench.mjs paired lite-d12-mp1 lite-d14-mp1
node bench.mjs report         # -> results.json + markdown tables (also saved in logs/report.md)
```

Options: --limit, --hash, --threads, --native-bin (or $STOCKFISH), --ref-depth/--ref-multipv/--ref-hash/--procs, --seed/--positions/--min-ply/--max-ply, --data, --out.

Total benchmark compute on this box was about 36 minutes: 8.2 min reference on 4 cores, plus 27.4 min summed over all the runs.

## Caveats

1) Measured in Node 22, not a browser (none is installed here). Node uses the same V8 WASM engine as Chrome, so desktop Chrome should be similar. Firefox, Safari and mobile were not measured; phones are likely several times slower. Init figures exclude the download (1.8 MB lite vs 99 MB full).

2) The reference is SF16 d22, but the builds under test are SF19, with a different net and eval scale. Native SF16 therefore gets a same-engine advantage on MAE, and full SF19's higher MAE (+0.37) likely reflects eval-scale differences, since its class agreement is identical to lite. The reference itself is noisy: SF16 d18 matches it on only 92.2% of severity classes, so ~90% is close to the ceiling.

3) The native baseline is Debian's generic "64bit SSE2" SF16 build (no POPCNT/AVX2), a slow native. "Lite WASM faster per node than native" (557-683 vs 516-524 knps) is specific to this binary, and lite's smaller net plays a part.

4) Test-set realism:
- 37% of pairs are uniformly random legal moves, mostly obvious blunders, which inflates the overall P/R.
- The non-random subset (283 pairs) has only 45 positives at loss >= 5 and 14 at loss >= 10, so its P/R values have very wide intervals.
- Positions come from named theory lines, not amateur games.
- There are ~3 candidates per position versus 1-2 in the real app; the MPV 1 vs 3 cost ratio for the 1-candidate case is derived, not measured.

5) Each config was run once, apart from two repeats. Hash state alone shifted lite d12 class agreement by ~3 points (85.8% single vs 88.9% on the pool, p=0.054), so treat differences of 3 points or less as noise. Per-position timings vary +-15-20% between runs; run totals vary within 4%.

6) The stockfish.js glue does not work inside Node worker_threads, so WASM engines ran as separate Node processes using the package's CLI mode. Same WASM, same V8.

7) 4 vCPUs under KVM. The near-linear pool scaling (3.86x with 4 engines) may not hold on SMT machines or when the main thread is busy.

8) Batching uncovered moves into a single multi-move searchmoves search was not measured; it is worth a follow-up.

9) Depth-18 ceiling rows were timed per engine while 4 engines ran concurrently; their p90 and knps are omitted here and are in results.json.
